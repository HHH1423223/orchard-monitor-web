# DESIGN-NOTES · 本轮视觉重构的过程记录与决策依据

> 这是给下一个执行者（人或 AI）看的"为什么"，`HANDOFF.md` 是"做什么"。
> 两份文件配套使用：先看这份理解动机，再照 `HANDOFF.md` 逐章执行。

---

## 1. 起点：这个项目原来是什么样

在动手之前，我通读了整个项目：`README.md`、`DESIGN.md`、五个视图、`store/monitor.js`、`utils/chart.js`、`oneui.css`，并且实际跑了 `npm run dev`，用 Puppeteer 截了 `login`/`monitor`/`control` 三页的真实渲染图核对代码和实际效果是否一致（结果一致，代码质量本身没问题）。

原项目的视觉是"三星 One UI 风"：大圆角（26px）、分层阴影、青绿主色、深色玻璃拟态曾被对比过但放弃了。这套视觉**做得很规整**，但正因为规整、正因为是"这年头 AI 一写大屏就长这样"的那套（圆角卡片+柔和阴影+青绿或蓝紫渐变+ECharts 深色大屏），放在比赛现场会和其他参赛队伍的作品高度撞脸——这正是用户最在意的问题："别到时候拿出来和别的参赛选手的作品看起来差不多"。

## 2. 我为什么选"农业数据台账"这个方向，而不是继续微调 One UI

用户要求"差异化"，同时项目本身有两个强约束：
1. 这是**真实农业监测数据**（墒情、水位、灌溉），不是消费级 App，装饰性动效和大色块渐变本身就和"数据可信度"这个诉求冲突。
2. 评委会近距离看细节（截图、投影、现场操作），不是远距离扫一眼的营销页——所以"克制"比"炫"更容易在近距离审视下经得起推敲。

据此排除了几个方向：深色玫瑃拟态（原项目自己在 `DESIGN.md` 里否定过，说会显得"通用大屏感重"）、渐变卡片、圆角气泡风（这三种都是当前 AI 生成界面最常见的三条路，撞脸风险最高）。

选定方向：**纸感台账**——暖白底、细实线分区（不用阴影分层）、衬线字体做标题（`Noto Serif SC`）、等宽字体做数据（`IBM Plex Mono`）、无渐变、无圆角光晕。这套语言更接近"农业统计报表/勘测档案"的气质，和"果园""刺梨""合作社"这些内容本身贴合，也天然和市面上千篇一律的"科技感大屏"拉开距离。

## 3. 配色：为什么不能凭感觉挑三个颜色

用户项目里有一个强需求点：9 个墒情点位分三个地形分区（坡顶/坡中/洼地），过去只靠色块循环上色（9 色调色板循环取色，和分区无关）。我把这改成了"按分区分组配色"，这样看图表时颜色本身就在传达"这是坡顶的点/这是洼地的点"，信息密度更高。

但三个分区色如果凑不好，色弱评委或者投影光照差的现场会分不清。所以我调用了项目里的 `dataviz` skill，用它自带的 `validate_palette.js` 脚本做了**真实的色觉可辨性校验**（不是我口头判断"这三个颜色看起来能分开"）。跑了大量候选组合（暖褐 × 苔绿 × 靛蓝的排列组合，脚本里能看到我写的 `search.sh` 暴力搜索脚本），挑出了零 WARN、CVD ΔE 9.0 的一组：`#b8741a`（坡顶）/ `#2e6e3e`（坡中）/ `#2f5fb8`（洼地）。这三个值已经写进 `HANDOFF.md` 第 9.1 节，**不要再换**，换了要重新跑校验脚本。

## 4. 字体选型：为什么是这两个包，不是别的

标题用 `Noto Serif SC`（衬线），数据用 `IBM Plex Mono`（等宽）。理由：
- 衬线字体是"台账/报表/档案"气质的关键信号，市面上的科技大屏几乎没人用衬线标题，这是差异化最直接的一刀。
- 等宽字体让所有数值列在视觉上对齐（尤其表格里的水分/pH/电压这些数字列），并且等宽字体本身带一种"仪器读数"的严肃感，和刻意加粗加大的花哨数字风格相反。
- 我实测过 `@fontsource/noto-serif-sc` 全量包接近 90MB（100+ 个字重的 woff2），所以在 `HANDOFF.md` 里明确要求**只装需要的字重**（400/700 两档），避免执行者图省事整包引入导致构建体积暴涨。这是我在写文档前用 `npm pack --dry-run` 实测出来的具体数字，不是猜的。

## 5. ECharts 按需引入：为什么单独起一个 utils/echarts.js

原项目 `main.js` 直接 `import * as echarts from 'echarts'`，全量包体积在 README 的"已知不足"里被诚实地写过（约 1MB，gzip 后 344KB）。用户提到的三条已知不足之一。这次顺手解决掉：只注册项目实际用到的 `LineChart`/`BarChart` + 必要 component + `CanvasRenderer`，改动只涉及一个新文件加 `BaseChart.vue` 的一行 import，风险极低、收益明确，所以纳入本轮范围。

## 6. 为什么新增 SlopeProfile 组件，而不是只改颜色字体

只换皮肤（颜色、字体、间距）能解决"撞脸"问题的一半，但评委看多了同类项目后，真正记得住的是**信息呈现方式**，不是配色。原项目里"坡顶3/坡中3/洼地2/水池边1"这个地形分布信息，只在文字里说了一句，9 个点位卡片本身是打散的网格，看不出空间关系。这是这个项目最独特的领域知识（洼地病害风险高于坡顶，点位按坡位布设——这句话原本就写在 `mock/devices.js` 的注释里），非常适合做成一张一眼能看懂的坡面剖面图，而不是继续埋在文字说明里。所以我设计了 `SlopeProfile.vue`：一张 SVG 坡面示意图，9 个点按坡顶→坡中→洼地→水池的相对位置摆放，颜色同时传达"哪个区"和"这个点状态如何"两层信息。这是本轮唯一的新增组件，其余改动都是存量文件的样式层修改。

## 7. 关于"只做视觉，不碰逻辑"这条线是怎么划的

用户原话强调了两条不可动的红线：① `store/monitor.js` 是唯一取数入口，不能破坏；② 三条联锁判断在前端，不能被当成"可以顺手加固"的东西去动。这两条我在读 `README.md`、`ControlView.vue` 顶部注释时就确认了项目自己也是这么写的（"前端能绕过的安全规则等于没有安全规则"），所以 `HANDOFF.md` 里第 0 章、第 10 章反复用不同措辞重申这两条，就是因为怕执行方 AI 在"顺手优化"的惯性下越界。凡是涉及五个视图脚本的改动，**唯一允许的改动**统一是"把 `from '../mock/devices'` 换成 `from '../store/monitor'`"这一类 import 路径调整，逻辑一行不碰。

## 8. 已知会被牺牲的东西（交接必须提醒对方）

- 原项目的阴影分层（One UI 的核心设计特征之一）被整体推翻为"无阴影，靠 1px 实线分区"。这是设计方向切换的必然代价，不是疏漏。
- 原项目折线的 `smooth: 0.35`（平滑曲线）被改成 `smooth: 0`（直线），柱状图圆角被改成直角。这是刻意的："如实记录"的台账气质要求数据点之间不做视觉美化的插值曲线。如果后续觉得直线太生硬，可以调，但别悄悄改回原来的柔和风格，那会和整体气质冲突。
- 深色模式在原 `DESIGN.md` 里被列为"未覆盖但可以后续做"的项，本轮**明确不做**（`HANDOFF.md` 红线第 4 条），避免执行方 AI 顺手加了反而破坏纸感台账的核心气质（暖白纸底换成深色后衬线字体和细线分区的效果会完全变样，不是简单换色能解决的）。

## 9. 交给 DeepSeek 之后，人工要重点盯的地方

1. `SlopeProfile.vue` 是全新代码，没有实际跑起来验证过（这轮会话没有编译执行这个组件），执行方接手后第一件事应该是跑起来看它是否正常渲染、9 个点位是否对得上实际的 `location` 字符串格式（`"东坡 · 坡顶"` 这种，中间的间隔符是全角空格+中间点+空格，容易在字符串分割时出错，务必实测）。
2. 色板校验只验证了"能不能分辨"，没有验证"和整体纸感背景放在一起好不好看"，执行方做完后建议截图看一眼三个分区色在暖白背景下的实际效果。
3. 字体只装了 400/700（衬线）和 400/500/600（等宽）几个字重，如果后续发现某处用到了没装的字重（比如衬线 500），会静默回退到系统字体，不会报错，容易被忽略，建议构建后目视检查一遍标题字体是否真的是衬线。
